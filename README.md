## 1. 建设目标与范围

建立从代码提交到生产发布、验证、回滚和审计的完整流程。

| 目标 | 验收标准 |
|---|---|
| 流程标准化 | Java、Python 服务分别使用统一流水线模板 |
| 制品一致性 | 测试、预发和生产使用同一个镜像 digest，不重复构建 |
| 发布可追溯 | 从线上版本追溯到代码提交、构建记录、镜像和审批记录 |
| 发布安全 | 生产变更经过授权审批，流水线和部署系统遵循最小权限 |
| 发布稳定 | 通过探针、滚动更新或灰度发布控制影响范围 |
| 故障可恢复 | 有应用回滚、配置恢复、数据库兼容和平台恢复流程 |
| 状态可观测 | 能判断发布结果，并关联日志、指标和告警 |

建设范围包括应用构建、镜像管理、配置管理、部署、验证、回滚及平台自身运维。数据库变更纳入发布流程，但数据库恢复不能简单等同于应用回滚。

## 2. 总体技术架构

### 2.1 Jenkins 与 Argo CD 的分工

- **Jenkins 负责 CI**：编译、测试、代码扫描、构建镜像、推送制品。
- **Argo CD 负责 CD**：按 Git 声明的配置部署应用，持续检查集群实际状态与期望状态是否一致。
- Jenkins 可以独立承担 CI/CD，但需要额外设计部署权限、漂移检测、审计和回滚。
- Argo CD 本身不编译代码、不构建镜像，仍需 Jenkins、GitLab CI 等 CI 工具配合。

推荐主方案为 **Jenkins + Argo CD + Harbor + Helm**，保留 Jenkins 单独部署的过渡路线。

### 2.2 交付链路

```mermaid
flowchart LR
    A[开发提交代码 / 合并请求] --> B[代码仓库]
    B --> C[Jenkins CI]
    C --> D[测试、代码扫描、依赖检查]
    D --> E[构建镜像、扫描、生成 SBOM]
    E --> F[Harbor 镜像仓库]
    F --> G[更新 GitOps 仓库中的镜像 digest]
    G --> H[环境变更审批]
    H --> I[Argo CD]
    I --> J[Kubernetes 测试 / 预发 / 生产]
    J --> K[发布验证、监控与告警]
    K --> L[继续发布或回滚]
```

### 2.3 建议选型

| 能力 | 建议方案 | 说明 |
|---|---|---|
| 代码托管 | 复用现有 GitLab/GitHub 等 | 支持分支保护、合并审批、Webhook |
| 持续集成 | Jenkins | 公共治理流程，分别提供 Java、Python 构建模板 |
| 镜像仓库 | Harbor | 镜像扫描、访问控制、保留策略 |
| 依赖管理 | Nexus 或现有私服 | 按需提供 Maven、PyPI 等代理与缓存 |
| 部署模板 | Helm | 统一部署结构，通过参数表达运行时差异 |
| 持续交付 | Argo CD | GitOps 同步、状态检查、差异展示 |
| 密钥管理 | 现有密钥平台，可对接 External Secrets | Git 中仅保存密钥引用 |
| 监控 | Prometheus + Grafana + Alertmanager | 优先复用已有体系 |
| 日志 | Loki 或 Elasticsearch 体系 | 与服务及发布版本关联 |
| 渐进式发布 | Argo Rollouts，可选 | 有灰度需求时引入；不是 Argo CD 自带能力 |

实施阶段根据 Kubernetes 版本、插件兼容性和安全维护周期确定工具版本。生产固定版本，不直接使用 `latest`。

## 3. 环境与权限隔离

### 3.1 环境规划

| 环境 | 主要用途 | 发布方式 |
|---|---|---|
| 开发/测试 | 快速反馈、自动化验证 | 自动部署 |
| 预发 | 验证部署、配置、数据库兼容性与发布策略 | 自动化结合验收 |
| 生产 | 正式业务服务 | 受保护的变更入口，审批后发布 |

生产建议使用独立集群。开发和测试可以根据资源条件共享集群，结合 Namespace、RBAC、ResourceQuota 和 NetworkPolicy 隔离。

Namespace 是管理边界，单独使用不能构成完整的安全隔离。预发应尽量保持与生产相同的软件版本、拓扑与关键配置结构；规模差异须记录，敏感数据须脱敏。

### 3.2 权限矩阵

| 主体 | 权限原则 |
|---|---|
| 开发人员 | 提交代码、查看构建；生产操作按岗位授权 |
| Jenkins | 读取代码、推送镜像、提交 GitOps 变更；主方案中不持有生产集群管理员权限 |
| Argo CD | 仅管理授权集群、Namespace 和资源类型 |
| 应用 ServiceAccount | 只授予业务必需权限；不调用 K8s API 时关闭自动挂载 Token |
| 发布审批人 | 审核生产变更，避免提交人自行批准关键发布 |
| 应急管理员 | 使用受审计的临时应急权限，操作后回写 Git |

不可信合并请求构建不能访问生产凭据。普通测试任务与拥有镜像推送、GitOps 写入权限的可信发布任务需要隔离。

## 4. 代码、部署配置与制品管理

### 4.1 仓库组织

建议分开管理应用代码和环境部署配置。

应用仓库示例：

```text
order-service/
├── src/
├── pom.xml
├── Dockerfile
├── Jenkinsfile
└── deploy/
    └── README.md
```

GitOps 仓库示例：

```text
platform-gitops/
├── applications/
│   ├── test/
│   ├── staging/
│   └── prod/
├── charts/
│   ├── java-service/
│   └── python-service/
└── environments/
    ├── test/order-service/values.yaml
    ├── staging/order-service/values.yaml
    └── prod/order-service/values.yaml
```

统一维护 Helm Chart，通过参数描述服务差异；特殊运行方式保留独立模板。Chart 的环境提升同样需要锁定版本，避免修改公共模板时无审批影响生产。

### 4.2 镜像标识与不可变制品

以下地址仅为示例：

```text
便于识别的标签：
harbor.example.com/business/order-service:1.8.0-a1b2c3d

部署实际引用：
harbor.example.com/business/order-service@sha256:<完整摘要>
```

管理规则：

1. 发布标签禁止覆盖，部署锁定镜像 digest。
2. 同一次候选版本只构建一次，各环境提升同一制品。
3. 环境差异通过配置注入，不把生产密码或环境地址打进镜像。
4. 基础镜像、构建依赖、Helm Chart、流水线公共库均使用明确版本。
5. Harbor 清理策略保留当前运行版本和约定的回滚版本。
6. 发布记录关联代码 SHA、构建编号、镜像 digest、Chart 版本和配置提交。

## 5. CI 流程设计

### 5.1 流水线阶段

| 阶段 | Java 服务 | Python 服务 |
|---|---|---|
| 源码获取 | 拉取指定提交，记录 SHA | 同左 |
| 依赖安装 | Maven/Gradle，使用公司依赖源 | 根据锁文件安装依赖 |
| 基础检查 | 编译、格式或静态检查 | 语法、Lint，按需类型检查 |
| 单元测试 | JUnit 等 | pytest 等 |
| 集成测试 | 验证数据库、缓存、消息等依赖 | 同左 |
| 质量检查 | 质量门禁、依赖漏洞、密钥泄露扫描 | 同左 |
| 制品构建 | 生成 JAR/WAR，再构建镜像 | 构建包含运行依赖的镜像 |
| 镜像检查 | 漏洞扫描、基础镜像与运行权限检查 | 同左 |
| 制品发布 | 推送 Harbor，记录 digest、SBOM | 同左 |
| 部署申请 | 修改 GitOps 镜像引用并提交变更 | 同左 |

质量平台和扫描工具复用现有能力；需要新建时可评估 SonarQube、Trivy 等，并验证语言、许可证和资源成本。

### 5.2 质量与安全门禁

- 必须通过的测试失败：阻断。
- 检出有效凭据泄露：阻断，并进入凭据处理流程。
- 不符合组织漏洞策略：阻断，或进入有责任人、有效期的例外流程。
- 质量门禁不通过：按服务接入阶段执行。
- 镜像来源不可信或缺少强制签名：阻断。

覆盖率不能替代测试质量。老服务可先对新增代码设置门禁，再治理存量问题。漏洞策略应区分严重程度、可利用性、修复可用性及例外时限，不能只有扫描报告而没有处理规则。

### 5.3 Jenkins 执行环境

- 使用 Kubernetes 临时 Agent，控制器不承担普通业务构建。
- 固定构建工具镜像及流水线公共库版本。
- 配置资源限制、任务超时、并发上限和构建保留策略。
- 普通构建任务不挂载宿主机 Docker Socket；选择符合隔离要求的镜像构建方式。
- 可信发布与不可信代码检查使用不同权限边界。
- 缓存按用途与信任级别隔离，避免污染可信构建。
- 失败时输出明确阶段、原因和定位链接，清理临时资源。

## 6. CD 与生产发布流程

### 6.1 标准流程

```text
代码评审通过
→ CI 构建与检查通过
→ 自动部署测试环境
→ 自动化验证
→ 将同一镜像提升到预发
→ 预发验收
→ 提交生产 GitOps 变更
→ 审批并合并
→ Argo CD 同步
→ 发布验证
→ 发布完成或回滚
```

生产选择一种主要控制方式：

- **Git 审批后自动同步**：合并受保护的生产变更即授权发布。
- **Git 审批后人工同步**：适用于明确发布窗口或额外变更管理要求。

审批点、操作者和授权含义须明确，避免重复且无实际作用的人工确认。同一服务、同一环境的发布应串行，避免新旧变更互相覆盖。

### 6.2 Argo CD 管理原则

- 使用 Project 限制仓库、目标集群、Namespace 和资源类型。
- 配置生产同步窗口。
- 审慎启用自动清理资源，保护关键资源免于误删。
- 自动纠偏与应急操作流程配套。
- 对不同步、健康异常、同步失败和长时间挂起配置告警。
- 配置差异忽略规则应最小化，不能以大范围忽略掩盖真实漂移。
- 发布顺序和迁移任务按应用依赖设计，避免把所有服务绑定为一次不可分割的大发布。

Argo CD 的 Synced/Healthy 不能替代业务验收。发布后还需验证登录、下单、查询等代表性链路，并检查错误率、延迟和依赖异常。

## 7. Java 与 Python 的 Kubernetes 运行规范

### 7.1 通用要求

- 明确 CPU、内存 Requests/Limits，并通过压测校准。
- 配置 Startup、Readiness、Liveness 探针。
- 实现优雅退出，设置合理的终止等待时间。
- 非 root 运行，限制容器权限；按兼容性采用只读根文件系统等措施。
- 日志输出到标准输出，携带服务、环境、版本、Trace ID。
- 按可用性目标配置副本及反亲和或拓扑分布。
- 按服务特性配置 HPA 和 PodDisruptionBudget。
- 验证扩缩容、节点维护、Pod 退出和下游连接释放行为。

PodDisruptionBudget 主要约束自愿驱逐，不能替代 Deployment 的更新策略，也不能防止所有节点故障。

### 7.2 Java 服务

- 使用支持容器资源识别且受维护的 JDK。
- JVM 堆不能占满容器内存，要给 Metaspace、线程栈、直接内存等留空间。
- 根据启动耗时设置 startupProbe，避免启动期间误重启。
- Spring Boot 等应用启用并验证优雅关闭，配合流量摘除处理在途请求。
- 滚动更新期间，新旧版本须能共同访问数据库、缓存和消息系统。
- 对 OOM、GC 停顿、线程池和连接池饱和建立监控。

例如：容器限制为 2 GiB 时，可从堆占容器内存约 60%～70% 开始压测，最终依据实际负载确定；不能作为全公司统一参数。

### 7.3 Python 服务

- 锁定依赖，区分构建依赖和运行依赖。
- 按框架选择生产服务器，不使用开发服务器。
- Worker 数结合 CPU 配额、内存和负载确定。
- API、后台任务、定时任务分别选择适合的 Deployment、Job 或 CronJob。
- 消费者退出时正确处理消息确认和重试，业务保证幂等。
- 定时任务明确并发策略、超时、补跑及失败处理方式。

### 7.4 探针设计

Liveness 应判断进程是否需要重启，Readiness 判断实例是否适合接收流量，Startup 为启动过程提供保护。

避免数据库短暂不可用触发全部应用 Liveness 失败，导致集体重启并放大故障。探针路径和阈值须按应用实际行为验证。

## 8. 发布策略与自动回滚边界

| 服务类型 | 建议策略 |
|---|---|
| 普通无状态内部服务 | Kubernetes RollingUpdate |
| 核心交易或重要接口 | 灰度发布，结合指标和人工判断 |
| 需要快速切换的服务 | 容量和数据兼容允许时使用蓝绿发布 |
| 消费者、定时任务 | 专门验证并发、重复执行、消息格式和幂等 |

普通 HTTP 服务可从以下配置开始验证：

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
```

该配置需要额外资源和准确的 Readiness 判断，不能单独保证零中断。蓝绿发布需要考虑双份容量、连接排空及回切兼容性。

灰度流程：

```text
少量流量 → 检查指标 → 扩大流量 → 再次验证 → 全量
```

具体比例、观察窗口和失败阈值根据流量及 SLO 制定。低流量服务需要足够样本或主动合成测试。

可靠的加权流量灰度须验证 Argo Rollouts 与现有 Ingress、网关或 Service Mesh 的集成；仅调整 Pod 数量不能保证精确流量比例。

自动回滚只适用于判断标准明确、旧版本可运行、数据兼容已确认的场景。分析系统不可用、指标样本不足时应暂停并人工判断，不能默认视为通过。

## 9. 回滚与数据库变更

### 9.1 应用回滚

回滚覆盖镜像、配置、Chart/清单以及数据和消息格式兼容性。

GitOps 模式下，通过受审计的 Git 变更恢复上一组已验证配置，再由 Argo CD 同步。优先做针对目标服务的回退，避免撤销同一提交中无关服务的有效变更。

仅执行 kubectl rollout undo 会造成 Git 与集群不一致，可能被重新同步覆盖。应急操作必须协调同步策略，并及时回写 Git。

回滚前确认：

1. 上一版本镜像和部署配置仍可获取。
2. 数据库、缓存、消息格式允许旧版本运行。
3. 密钥和外部依赖没有发生不兼容变化。
4. 没有其他进行中的发布覆盖回滚目标。
5. 回滚后执行相同级别的健康与业务验证。

### 9.2 数据库迁移

使用 Flyway、Liquibase 或项目已有工具，通过受控的单独任务执行；不要让所有应用副本在启动时无序执行迁移。

```text
新增兼容结构
→ 部署兼容新旧结构的应用
→ 数据回填并验证
→ 切换读写
→ 观察
→ 后续版本清理旧结构
```

迁移任务需具备版本记录、并发控制、失败停止机制和可审查脚本。大表变更评估锁等待、执行时间和业务影响；数据回填考虑限速、断点续作及校验。

不要把删列、改类型等破坏性操作与新应用上线绑定为一个不可撤销步骤。

数据库恢复到备份可能丢失上线后的有效写入，需要独立恢复决策和演练，不能作为默认自动回滚动作。

## 10. 安全、审计与供应链治理

- Git 启用受保护分支、审批规则及重要操作审计。
- Jenkins、Argo CD、Harbor 对接统一身份认证，按职责授权。
- 凭据集中管理、定期轮换，禁止在构建日志中明文输出。
- Git 和普通 Helm Values 不保存明文密码、Token、私钥。
- Kubernetes Secret 的 Base64 编码不等于加密；配套 RBAC 和静态加密。
- 镜像仓库区分推送和拉取身份，权限限制到项目。
- 网络规则限制构建任务、应用访问不必要的内外网地址。
- 镜像扫描、SBOM、制品来源记录纳入发布证据。
- 引入签名时，同时建立签名身份、信任策略和准入验证。
- 准入策略先验证兼容性，再逐步从审计转为强制。
- 应急例外设置责任人、适用范围、有效期和复盘记录。

每次生产发布至少保存代码 SHA、构建编号、镜像 digest、部署配置提交、审批人、执行结果、验证结果及回滚记录。

## 11. CI/CD 平台自身的可靠性

平台组件故障通常不应影响已运行的业务，但会影响构建、发布及故障修复。

| 组件 | 建设重点 |
|---|---|
| Jenkins | 控制器配置、凭据及必要数据备份；插件版本治理；临时 Agent |
| Argo CD | 按规模采用 HA；保存声明式配置、集群接入信息与恢复方式 |
| Harbor | 镜像存储、数据库、证书和配置的备份及一致性恢复 |
| Git 平台 | 仓库、权限、审批规则及相关元数据恢复 |
| 密钥平台 | 独立灾备、解封或恢复流程、访问审计 |
| 依赖私服 | 存储、缓存容量、上游故障处理及清理策略 |

Jenkins 开源控制器不能通过简单增加同一个 Deployment 的副本数实现可靠主动多活。可先采用稳定单控制器、快速恢复，再按规模拆分控制器。

补充要求：

- 规划 CI 并发、构建资源、存储和网络带宽。
- 评估 Harbor 镜像增长、复制与保留策略。
- 建立平台升级、插件升级、证书到期检查机制。
- 按业务需要确定各组件 RPO/RTO，执行实际恢复演练。
- 制定 Git、Harbor、Argo CD 不可用时的发布和应急预案。
- 备份与平台故障域隔离，限制访问并验证可恢复性。
- 平台重建应避免循环依赖：恢复所需镜像、配置、凭据和操作手册必须有可用获取路径。

## 12. 监控指标与生产验收

### 12.1 监控指标

| 方向 | 关注指标 |
|---|---|
| CI | 排队时长、构建耗时、失败率、Agent 资源使用 |
| CD | 同步失败、状态漂移、发布耗时、卡住的 Rollout |
| 应用 | 可用性、错误率、P95/P99 延迟、重启和 OOM |
| 依赖 | 数据库连接池、消息积压、缓存错误 |
| 交付效果 | 部署频率、变更前置时间、变更失败率、恢复时间 |

指标按服务、环境、版本展示，发布事件写入监控时间线。告警应包含责任团队、影响环境、定位入口和处置手册。

### 12.2 验收清单

- [ ] 正常变更通过标准流程发布，且全链路可追溯。
- [ ] 测试失败或不符合安全门禁的制品无法进入生产。
- [ ] 测试、预发和生产使用同一镜像 digest。
- [ ] 未通过发布验证时停止继续扩散。
- [ ] 镜像、配置和模板可以恢复到已验证版本。
- [ ] 数据库迁移失败时，新版本不会继续错误上线。
- [ ] 不可信构建无法读取生产凭据或修改生产部署。
- [ ] 可以发现人工修改产生的配置漂移。
- [ ] 节点维护、Pod 退出及扩缩容符合可用性要求。
- [ ] 并发发布不会覆盖其他有效变更。
- [ ] CI/CD 关键组件的备份经过实际恢复验证。
- [ ] 告警能到达对应责任人，处置流程可执行。
- [ ] 回滚版本未被仓库清理策略删除。
- [ ] 发布记录、审批记录和例外记录符合审计要求。

发布耗时、恢复时间等数值先测量试点服务，再形成正式承诺。

## 13. 实施路径

| 阶段 | 主要工作 | 交付物 |
|---|---|---|
| 现状调研 | 清点服务、集群、网络、权限及发布流程 | 现状清单、风险清单、架构决策 |
| 平台基础 | Jenkins、Harbor、Argo CD、GitOps、身份权限 | 可用平台、备份方案、权限矩阵 |
| 试点接入 | 典型 Java 服务和 Python 服务 | 流水线、Chart、发布与回滚记录 |
| 生产治理 | 审批、门禁、监控、密钥、灾备 | 发布规范、故障预案、验收报告 |
| 批量推广 | 按服务类型及风险分批接入 | 接入清单、培训文档、运营指标 |

试点应覆盖真实差异：启动慢的 Java 服务、带数据库迁移的服务，以及 Python API 或任务服务。不能仅凭简单演示应用证明方案成立。

建议责任分工：

| 角色 | 主要责任 |
|---|---|
| 平台运维 | 平台可用性、模板维护、权限、备份、监控 |
| 应用研发 | 测试、健康检查、优雅退出、数据兼容、业务验证 |
| 测试人员 | 自动化验证、预发验收、回归策略 |
| 安全人员或指定责任人 | 安全门禁、漏洞例外、凭据治理 |
| 发布负责人 | 变更审批协调、发布决策、回滚决策与记录 |

推广门槛：试点完成正常发布、失败阻断、应用回滚、数据库兼容及平台恢复演练，再分批接入生产服务。

## 14. 仅使用 Jenkins 的过渡方案

```text
提交代码
→ Jenkins 测试与构建
→ 推送 Harbor
→ 测试与预发部署
→ 生产审批
→ Jenkins 调用 Helm 部署
→ 业务验证
→ 必要时回滚
```

需要额外补齐：

1. 按环境隔离部署凭据，避免共享管理员 kubeconfig。
2. 同一服务、同一环境加发布锁。
3. 保存镜像、Chart、Values、审批及执行记录。
4. 固定 Helm 版本，验证等待、超时和失败恢复行为。
5. 建立配置漂移检测。
6. 单独处理数据库迁移；Helm 回滚不能撤销数据库操作。
7. 明确 Jenkins 不可用时的受控应急发布流程。

后续引入 Argo CD 时，保留 Jenkins CI，把部署执行权逐步迁移到 GitOps。

**禁止 Jenkins 和 Argo CD 同时管理同一应用的相同资源。**

## 15. 入职调研与待决策事项

| 项目 | 需要确认的内容 |
|---|---|
| 现有工具 | 代码平台、镜像仓库、依赖私服、监控、日志、密钥平台 |
| 工具约束 | Jenkins 与 Argo CD 是否可组合使用，还是必须限定选型 |
| 集群情况 | K8s 版本、集群数量、节点规模、存储、网络及配额 |
| 服务情况 | 服务数量、Java 框架/JDK、Python 运行模式、构建工具 |
| 网络入口 | Ingress/网关类型，是否具备灰度流量控制能力 |
| 业务等级 | 核心链路、SLO、发布窗口、容忍中断时间 |
| 数据变更 | 数据库类型、迁移工具、兼容规范、备份与恢复能力 |
| 身份权限 | SSO、审批责任、生产操作和应急权限机制 |
| 当前痛点 | 构建慢、发布失败、手工操作、回滚困难或缺少审计 |
| 容量预算 | 构建并发、存储增长、平台 HA 和灰度容量预算 |
| 合规要求 | 审计保留期、数据分级、漏洞策略、制品签名要求 |

技术评审应明确最终选型、职责边界、生产发布授权方式、回滚条件、实施批次和验收标准；尚未验证的参数保留为待确认项。
